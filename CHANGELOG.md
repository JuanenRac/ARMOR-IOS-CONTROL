# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **What a widget of the home screen says about the system is ready, as the Android tile and widget do:** the face (armed, disarmed or no data, from the word of the server for the mode and nothing else) and its three words in the eight languages are in the core, and the source of a small widget that shows it and opens the app sits in `docs/widget`, apart from the app target until a Mac builds it: it can only show, never arm or disarm.
- **The status screen counts the nodes of every kind, as the Android app does:** besides the radar nodes of the live stream it takes the health every solar, electrical, alarm and wall-panel node reports, counts a node that is in both lists once (online when either says so), and shows "online out of all" with the count of each kind; a tap opens the health of the nodes. Eight languages.
- **The copy of the shared contract follows the summary of a solar gateway:** `ArmorContract.swift` is again what ARMOR-COMMON generates, with the reader of the summary a solar gateway sends and of the alerts it raises on its own.
- **A notice about a camera can carry its picture, taken from your own server, as the Android app does:** a switch in the notice settings (off by default) makes the phone, when the notice of a camera that stopped answering is shown, replace it quietly with the same notice and the still picture of that camera attached (`GET /api/v1/cameras/{id}/snapshot` with the saved session, at most 1.5 MB, only if the bytes are a JPEG or PNG). The picture never goes through a push service, nothing is kept, and without a session, an operator role or an answer the notice stays as it was. Two phrases in the eight languages. The "Open camera" action of this notice is still to come (it needs a tab selection and a camera route in the app).
- **The phone can tell the server whether it is home, with only a word, as the Android app does:** a switch (off by default, apart from the reminder on leaving) makes the phone send `home` when it enters the circle around the saved place and `away` when it leaves it (`PUT /api/v1/presence/me`, behind the server option `presence.by_user`); the circle is the one of the reminder, the place never leaves the phone, the side the phone is on is announced when the circle is registered, and any other word is refused locally. Two phrases in the eight languages.
- **A notice from the push can acknowledge its alarm without opening the app, as the Android app does:** the notice of an alarm the server named carries the action "Confirm" (a category with the action and the id of the alarm in its user info, checked before it is acted on); touching it reaches the server, tries the kept session and acknowledges the alarm, and shows nothing if it fails. The camera shortcut of the notice is still to come. Tests of the ids accepted, the user info and the category.
- **The permission texts of the location and the camera are in the eight languages:** the two location permissions of the reminder on leaving home were shown in English only; they are now in `InfoPlist.strings` of every language, and the camera text also says that the camera reads the set-up QR code of an installation.
- **The sign-in reads the QR code that sets up the app, as the Android app does:** a button scans the code Studio shows (the address of the installation, the fingerprint of its local authority and a code of one use that lives five minutes; no password, no session), asks the server for the same two facts with the code, and only when they agree sets the address, drops the away address of the one before and asks for the user and the password. The fingerprint is waited for by that connection: a chain that holds exactly that certificate pairs its key, so a private authority needs no installing on the phone; it never refuses a connection by itself. Tests of the text of the code, the agreement with the server's answer and the pairing; four new phrases in the eight languages.
- **The sign-in offers the servers whose session is kept on the phone, as the Android app does:** above the address fields there is a row with each server the person has signed in to, the one in use marked; one touch sets its address, drops the away address of the one before and tries the kept session, so going back to a server does not ask for the password again. A session the server refuses is now forgotten for the server that was tried, not for the one that happened to be in use. The row is not shown while no session is kept. Tests of how a server is written, the installation it makes and the list offered; two new phrases in the eight languages.
- **The session of each server is kept in the Keychain, not only the last one, as the Android app does:** the session of the server in use stays where it was and each server also has a place of its own, with a list of the servers (`origins`), `forget(origin:)` for one of them, signing out forgets only the one in use, and the way out of a locked app forgets them all; a session kept before the list existed still loads, and the option that ties the secrets to the unlocking of the phone moves every one of them. Tests of the several servers, the sign-out, the old place and the unlock option.
- **A reminder when the phone leaves home with the alarm disarmed, as the Android app has it, off until the person turns it on:** More > Reminder when leaving home has a switch and a button that saves the place the phone is in as home; the app then watches a circle of 150 m around it (region monitoring, which wakes the app even when it is closed) and, when the phone goes out of it, reads whether the system is armed and says so in a notice ("Arm the alarm?", or "Check the alarm" when the server cannot be read, so a failure is never silent); a second reminder waits 30 minutes. The place stays in the preferences of the app and is never sent to the server. Needs the location permission (while in use, then always), asked for only when the switch is turned on. The explanations of the two permissions are in English only for now: localized files for them are still to be written. Tests of the decision and of what is kept, in the 8 languages.
- **A hidden panic gesture, only while the server offers it, as the Android app has:** a long press on the shield of the status card, or five quick touches on it inside three seconds, asks the server for the silent duress alarm of the signed-in person (`POST /api/v1/alarm/panic-gesture`). The app listens for it only when the session says the administrator turned on the option `client.panic_gesture` (off by default) and the person may operate; nothing shows or sounds whatever the answer, it goes without the fingerprint or face prompt, the route leaves no line in the diagnostic report, a 404 makes the app forget the gesture, and a lost connection is tried once more after two seconds. The phone has no logo mark in a top bar as Android has, so the gesture is on the shield of the status card. Tests of the touch counter, the session fact, the silence, the viewer, the 404 and the report.
- **The copy of the shared contract is brought up to date:** `ArmorContract.swift` is again what ARMOR-COMMON generates (the vision event has a ceiling for the number of the followed object), and so are the table of the words of the alarm codes and the table of the help of the alarm codes (five codes of the energy balance), which the conformance test and the lint compare.
- **The app follows the small live notices of the server, as the Android app does:** while it is polling it keeps the WebSocket `/api/v1/events` open (the session cookie in the request, the certificate rules of the app, reconnecting after two seconds and doubling up to a minute) and a notice (an alarm, a device, a solar device, a network node or a design changed, with only its type, id and version) makes it read again at once; a burst is one read, and while notices arrive (one in the last minute) the asking slows to thirty seconds and goes back when none comes, so a server that has the option off loses nothing. Messages of a kind the app does not know are ignored. Tests of the parsing, the address, the reconnection delays and the pace of the asking.
- **The pictures of the app are taken by a UI test on a simulator:** the sign-in carries accessibility identifiers, the project has a UI test target `ARMORUITests` (skipped when no server is given) that signs in against a real server and goes through the sections of the bar at the bottom taking a picture of each, and the workflow `ios-shots.yml` (by hand or on a branch `shots-run/<name>`, never on main) starts a real server on the Mac, runs it on an iPhone simulator and keeps the pictures as an artifact; the first pictures are in `images/screenshots`.

## [0.0.5] - Tolerant contract readers, spoken orders and phone recordings

- **The daily summary, the heat map and the connected clients are read through the shared contract, ignoring members the app does not know:** `Contract.parseTolerant` (new file `Contract/ContractTolerant.swift`) drops, at every level, the members that a closed object of the schema does not name and then reads the message with the generated reader, so a newer server that adds a member does not empty a screen; a document that is really wrong (a missing member, a wrong value, a bad pattern) still gets nothing, and then the readers written by hand take over as before. Three new tests run it against the conformance vectors of ARMOR-COMMON (every valid case with an unknown member in each closed object reads the same, every wrong case stays refused). Written without compiling (no Mac): the proof on a Mac is pending.
- **The generated readers of the shared contract follow:** they know the optional `stack_min_free` and `stack_min_task` of the node health report.
- **Readers and writers of the messages, generated from the shared schemas (as on Android):** `Sources/ArmorCore/Contract/ArmorContract.swift` is the file ARMOR-COMMON generates, with a struct for every message (`init(reading:)` and `toJSON()`), `Contract.check` (the same keywords and order of checks as the other readers), `Contract.parse`, `Contract.parse<Message>` and `Contract.rewrite`. Nothing the app does today changes: the readers written by hand stay in place and the generated ones are ready to replace them one screen at a time. Eight new tests run `conformance/wire_cases.tsv` and `conformance/wire_full_cases.tsv` through them: the same verdict as the Python validator on every case, every valid case read into its struct, written back equal to the document without the members the schema does not name, and the same text when written twice; another test fails when the copy is not what ARMOR-COMMON generates. The workflow "Swift tests" fetches ARMOR-COMMON next to the repository and fails, instead of skipping, when it is missing.
- **The readers of the screens are tested against a real server:** the workflow "Swift tests" has a job, run on demand, that starts the real ARMOR-SERVER on the runner with an administrator of its own and runs the new `ServerLiveTests` against it: a wrong password is refused, the administrator signs in and reads the state, the lists of a fresh server are empty and not errors, and each reader behind a screen (history, devices, cameras, alarm panels, solar, electrical, battery, network, services, node health, connections, site, node control, machine update, sessions, second factor, remote access) either reads what the server sends or gets a refusal with a status. Without a server the tests are skipped, so the normal run does not change.
- **A spoken turn from the phone, off by default (as on Android):** a switch in More (*Orden hablada al servidor*, in the eight languages) adds a second button to the Assistant. It records one phrase with AVAudioEngine (up to ten seconds of 16 kHz mono sound, after the system asks for the permission of the microphone the first time the button is tapped), sends it raw to `POST /api/v1/voice/turn` with the voice token (typed once and kept in the Keychain, readable only while the phone is unlocked) and drops it, and shows the number of the challenge mode of `voice.silence_confirmation` on the screen for nineteen seconds, as the wall panel does, without ever saying it. With the switch off the app never opens the microphone, never asks for the permission and never sends a sound; a refused permission, a missing token, a viewer, an answer that is not a voice reply and a number that is not two to six digits all end the turn without showing anything. The last fifty events are written to a short audit trail on the phone (no words, no sound). `docs/CLIENT_BOUNDARY.md` explains how this changes what the phone fails closed on. `NSMicrophoneUsageDescription` is in the eight languages. 21 tests in ArmorCore cover the switch, the permission, the token, the expiry and the malformed number.
- **The challenge mode of the voice silence option is covered:** the server can now ask the voice service for a number that is shown on the wall panel and never said aloud. A written command that silences the alarm still asks for the signed confirmation and never less (only the spoken turn above shows the number); a test keeps that answer.
- **The recordings of the cameras, on the phone:** the same as the Android app. More > Recordings lists the photos and videos the server keeps, with the camera, the day, the size and a mark for the cameras recording now; "View" takes the file to a temporary copy of the phone and shows the picture or plays the video (the copy is removed when it is closed, and a file over 400 MB is refused), and an operator can delete one after being asked. A viewer sees no delete button, a refused list or file is told in words, and an empty library says so. The reading of the list, the route of each file (photos and videos live in different folders, every piece of the path escaped), the day and size shown and the calls to list, fetch and delete are rules of `ArmorCore` with tests. Texts in the eight languages. Written without a Mac: the screen is built by the manual job but not yet seen on a device.
- **A firmware image made for another board is refused in the words of the person, as in Studio:** the answer `wrong_board` of the server now has its own phrase (in the eight languages) next to `bad_proof` and the other codes of the security screens, instead of the general "it did not work"; a test covers it.
- **The sheet that asks for the proof of identity again and the pairing QR code are tested:** the rules of the sheet (the button works with a password or a code, a code of only spaces is nothing, the code is sent without spaces) moved into `ArmorCore` as `ElevationForm`, and the drawing of the pairing QR code moved there as `QrImage`, which also reads a still picture back, so a test draws the code and reads it with no camera. The app gets its own test target (`ARMORTests`, run inside the app on a simulator) that checks the sheet answers and closes, draws itself, and that the QR code the app draws reads back. A second manual job of the "Swift tests" workflow (`test_app`) generates the Xcode project and runs it; nothing runs on a push. Tests: 338 (before 330), 5 of them need a Mac.
- **A manual job runs the ArmorCore tests on an iPhone simulator:** the workflow "Swift tests" gets the input `test_on_simulator` (off; it never runs on a push) that picks an installed iPhone simulator on a macOS runner and runs `xcodebuild test` for the package, next to the `swift test` of every push. It checks the code on the platform of the app, not the screens on a phone.
- **Update the machine from the phone:** the same as the Android app. More > Update the machine (administrators only) shows the programs the maintenance helper can update, checks what is installed against the newest release without changing anything, and applies the update of one program after its name is typed again, the one-time code of the administrator, the lock of the phone and, outside the house, a new proof of identity. The plan of the check is good once and counts down on the screen, the job shows its steps, bar and log, every refusal of the server has its own words, and the screen offers nothing while the server or the helper has the switch off (the default). Only a signed release is ever put in place. Texts in the eight languages. Written without a Mac: not yet seen on a device.

## [0.0.1] - The iPhone client of ARMOR-SERVER

- **A SwiftUI app for the iPhone** with the same job as the Android one: sign in to the server of the house, see whether the system is armed, arm and disarm it, confirm alarms, command the alarm panels and watch the cameras. It speaks the same HTTP contract as the Android client and Studio, and nothing else.
- **The rules live in a Swift package (`ArmorCore`) with no UIKit or SwiftUI in it**, so they are tested without a phone and on Linux: the HTTP client, the models and their tolerant parsing, the choice of address, the lock of the phone, the vault of the session, the trust in the certificate, the alarm policy, the use cases (`ArmorController`) and the cutting of a live MJPEG stream. 98 unit tests, run with `swift test`.
- **Two addresses, at home and away:** the private address on the home Wi-Fi, the one for away from home (a name that follows the house, or the VPN) on mobile data; if the chosen one does not answer the other is tried, and the message says exactly what failed ("home cannot be reached", a changed certificate, no network).
- **Plain HTTP only to the local network:** a host that merely starts like a private address, a leading zero or a public address is refused, and the sign-in explains why and what to use instead (https, a dynamic DNS name).
- **Trust in the certificate of the installation:** the key of the certificate authority (or of the server's own certificate) is remembered the first time, or paired by pasting the text of the QR code of Studio; if it changes the connection is refused and the person told. Several keys can be kept for a renewal.
- **Lock with the phone (Face ID, Touch ID or the passcode):** asked before arming, disarming, silencing a siren, unlocking, ordering a device and confirming an assistant command (on by default only when the phone has Face ID or Touch ID), and, if the person turns it on, to open the app, with a time away after which it locks again. The server can raise it (`client.device_lock`) and never lower it, a phone with no passcode is never shut out, and the locked screen always offers "I cannot: sign in with the password".
- **Optional, off by default and with a visible warning:** the saved session and the remembered sign-in readable only while the phone is unlocked; what is kept is left alone while the phone is locked and moved to the other class when the switch is turned, which is asked with the lock of the phone.
- **Remember me** keeps the user and the password in the Keychain of the phone (this phone only, no backup, no iCloud); without the tick nothing of them is kept. The session cookie is kept the same way and renewed while in use.
- **Second factor and proof of identity:** the code of the authenticator app (or a recovery code) when the account has it, and the new proof of identity the server asks for critical actions from outside the house.
- **The assistant,** written commands to the voice service of the server with the confirmation bound to the person for arming and disarming, behind the lock.
- **Alarms that reach the phone:** notices for a node reaching HIGH, a silent camera, a device or equipment alarm and, while armed, a node that goes offline or silent; the alarm of a duress PIN is never shown or announced. Each event is announced once whether it arrives by reading or by push (the id of the event is the key), and the first reading only records where the history stands. Pushes through Firebase are optional and need the Firebase file of the installation.
- **Cameras:** a grid where only the pictures on screen run (six at most), a full view with a pad to move the camera and a snapshot, and a stream that is asked for again after 1, 2, 4... seconds (30 at most) when it drops. The picture comes from the server: the app never has a camera password or an RTSP address.
- **Devices** with On / Off, a confirmation for a circuit or a critical device, and the status, history and preflight of arming ("what would be left blind or noisy").
- **Eight languages** (English, Spanish, German, French, Italian, Japanese, Chinese and Portuguese of Portugal) for every text, the help, and the permission texts of the system; a check keeps every phrase of the sources in all the tables.
- **Checks that need no Mac:** `tools/ios_lint.py` verifies the structure of the project, the eight tables against the phrases of the sources, that the app calls only paths the Android client calls (and that the OpenAPI of the common repository knows them), the permissions, and that no secret or camera address is in the sources.
- **What it does not do:** it does not watch in the background (iOS does not allow a closed app to query the server), so alarms reach a closed app only through push; it has not been run on a device yet.
