# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **Solar, batteries and the electrical network, for administrators and operators:** the same as the Android app. More > Solar shows the sums (sun, consumption, state of charge, grid) and every inverter and battery with its numbers, its cells, its protection counters and its event log; More > Electrical shows the grid input, the circuits and the DC buses with the transfer switches; More > Battery maintenance (administrators only) offers the simple operations on a Pylontech battery in two steps: the node reads and checks the battery, the screen shows exactly what will be done, and it is written only after the serial number is typed again. The models, parsers and wording are in the core library with their tests, the texts are in the eight languages (Portuguese of Portugal included) and the pace at which each screen asks the server again is kept in `Resources/polling.json`, not in the code. The reports, the solar, electrical and battery calls are now declared in the protocol of the server API, so a call made through it reaches the real client (the reports were reaching a default that always refused). Not compiled or run on a device: it was written and checked with the repository's own lint, and the unit tests run in the macOS workflow.

- **The detail of every alarm shows its help text:** the same as the Android app, from the copy of the shared table, which now has the help of all the alarm codes.

- **The summary of a day and the activity heat map, for administrators and operators:** More > Reports (not offered to a viewer or a wall panel's account) shows the summary of a day with its counts, patterns and text in the language of the app, and the heat map of a camera as a picture with its caption. Each report is off in the server until an administrator turns it on; what the server answers when it is off, not set up, busy, failing or asked too often is told in words that say what to do. Eight languages, Portuguese of Portugal included. Not compiled or run here: it was written and checked with the repository's own lint, without Xcode.
- **The detail of an alarm shows the help of its code and the false-alarm mark:** the same as the Android app: the table every client shares (`alarm_facts.json`, a copy of the one in ARMOR-COMMON) holds, besides the labels of the facts, what each alarm code means and what to check in the eight languages; the detail shows it, and says when a person marked the alarm as a false alarm in Studio (the app only reads the mark). Not compiled or run here: it was written and checked with the repository's own lint, without Xcode.
- **The detail of an alarm:** the same as the Android app: the button Details of an alarm (active or closed) opens a sheet with its severity, source, time and state and every fact it carries with its label in the language of the app. The labels are the table of the contract (`alarm_facts.json`, a copy of the one in ARMOR-COMMON kept equal by a test and by `tools/ios_lint.py`), read in the core library (`AlarmFacts`); a fact the table does not know is shown with its key as it comes. The Swift tests of the core library are written and run by the macOS workflow.

- **An alarm panel that does not confirm the arming mode is told in the alarm list:** the same as the Android app: the alarm `mode_panel_sync_failed` reads in the language of the app from the shared table of alarm sentences (the copy in the resources is the one of the contract).
- **The home screen shows what the alarm panels did about the arming mode:** the same as the Android app, read in the core library (`panel_sync`) and shown as one line with the panels that did not confirm; nothing against a server that does not send it. The texts are in the eight languages.

- **Arming in a mode runs the check before arming:** the same as the Android app. The rule that decides when the picker shows the check (only an arm from disarmed, and only when the check found something) is now one function of the core library, with its test. The code and its tests are written and were not compiled or tried on an iPhone.

- **Arming modes of the server (Away, Home, Night):** the same as the Android app. While the server has the arming modes on, the arm button of the status screen opens a picker to arm in a mode, switch between modes or disarm; a mode with nothing assigned asks to be confirmed, a change to a mode that defends less asks for the PIN, and the status names the mode in force. Against an older server or with the modes off nothing changes. The check before arming is kept when arming from disarmed. The code and its tests are written but were not compiled or tried on an iPhone.

- **The lights of Project status follow the evidence of the manifest:** the manifest says how far the repository has been shown to work (`evidence`: `host-test`, `simulator`, `bench` or `field`) and the validator fails when a light is above what that evidence and the maturity allow (`tools/status_lights.py`), so a green that never ran on real hardware cannot come back.
- **The alarm notices show while the app is open:** a banner and the sound of the notice appear in the foreground too (before, the system showed nothing while the app was in front); what the person chose about hiding or silencing a notice still comes first.
- **Choose which notices the phone shows:** in More, "Which notices I want" can silence every notice, show them without sound (and without the voice), and switch off a severity or a kind of notice (radar alerts, cameras, nodes, and the alarms of devices, solar, electrical, network and alarm panels). A critical alarm is never taken away by severity or kind, only by the switch that silences everything. Everything stays in the history. Off by default: nothing changes until the person turns something off. The rules are `NoticeSettings` in `ArmorCore`, with unit tests.
- **A sound for each severity and each kind of notice:** a sound file of the person's own (.aiff, .wav or .caf, under 3 MB and 30 seconds, the formats iOS plays for a notification) is kept in the sounds of the app and named by the notification, with a play button; the kind wins over the severity, and the default sound of each severity is the way it was. iOS gives an app no list of its own sounds, so there is no list of phone sounds as on Android.
- **The voice that says the alarms:** woman or man, age, style, speed and whether low-severity notices are said too, the same choices as Studio and the Android app, with a test button and the existing "say the alarm aloud" switch (off by default) kept next to it. The pitch and pace are worked out in `ArmorCore` and given to the system speech synthesizer; the app speaks only while it is open.
- **A camera with two lenses in one picture is shown as two windows,** each with its half of the picture and the name of its lens; the snapshot and the movement pad still go to the real camera.
- **The new texts are in the eight languages,** and the tests cover the rules of the notices, the sounds, the voice and the lens windows (146 tests in all).

- **The README follows the universal layout:** security, interfaces, configuration, testing, troubleshooting and roadmap sections and the architecture and repository-structure pictures, in the eight languages.
- **The layout of the README is checked in the CI:** the validator runs the shared `tools/universal_readme_check.py` and fails when the README differs from the universal layout.
- **One table of alarm codes for every client:** the sentence of each alarm code (58 of them, in the eight languages) comes from a copy of the table that the server and Studio share, checked against the original by `tools/ios_lint.py` and by a test.
- **The quality of the camera picture is asked for explicitly:** a tile of the grid asks the server for the lighter picture from outside the house and the normal one at home, the full view lets the server decide.
- **The pictures of the README come from shared tools:** `tools/make_architecture.py` draws `images/architecture.svg` from `docs/architecture.json` and `tools/make_structure.py` draws the Repository Structure (the text tree and the animated picture) from `docs/structure.json`; both measure every text, and `--check` fails when a picture, its description or the code it points to disagree. They are vendored from ARMOR-COMMON like the shared CI checks.
- **The documentation covers the notices in the open app:** the README (eight languages) says the notices also show a banner and play their sound while the app is open, and the structure counts the 15 test files.

## [0.0.1] - The iPhone client of ARMOR-SERVER

- **A SwiftUI app for the iPhone** with the same job as the Android one: sign in to the server of the house, see whether the system is armed, arm and disarm it, confirm alarms, command the alarm panels and watch the cameras. It speaks the same HTTP contract as the Android client and Studio, and nothing else.
- **The rules live in a Swift package (`ArmorCore`) with no UIKit or SwiftUI in it**, so they are tested without a phone and on Linux: the HTTP client, the models and their tolerant parsing, the choice of address, the lock of the phone, the vault of the session, the trust in the certificate, the alarm policy, the use cases (`ArmorController`) and the cutting of a live MJPEG stream. 98 unit tests, run with `swift test`.
- **Two addresses, at home and away:** the private address on the home Wi-Fi, the one for away from home (a name that follows the house, or the VPN) on mobile data; if the chosen one does not answer the other is tried, and the message says exactly what failed ("home cannot be reached", a changed certificate, no network).
- **Plain HTTP only to the local network:** a host that merely starts like a private address, a leading zero or a public address is refused, and the sign-in explains why and what to use instead (https, a dynamic DNS name).
- **Trust in the certificate of the installation:** the key of the certificate authority (or of the server's own certificate) is remembered the first time, or paired by pasting the text of the QR code of Studio; if it changes the connection is refused and the person told. Several keys can be kept for a renewal.
- **Lock with the phone (Face ID, Touch ID or the passcode):** asked before arming, disarming, silencing a siren, unlocking, ordering a device and confirming an assistant command (on by default only when the phone has Face ID or Touch ID), and, if the person turns it on, to open the app, with a time away after which it locks again. The server can raise it (`client.device_lock`) and never lower it, a phone with no passcode is never shut out, and the locked screen always offers "I cannot: sign in with the password".
- **Optional, off by default and with a visible warning:** the saved session and the remembered sign-in readable only while the phone is unlocked; what is kept is left alone while the phone is locked and moved to the other class when the switch is turned, which is asked with the lock of the phone.
- **Remember me** keeps the user and the password in the Keychain of the phone (this phone only, no backup, no iCloud); without the tick nothing of them is kept. The session cookie is kept the same way and renewed while in use.
- **Second factor and proof of identity:** the code of the authenticator app (or a recovery code) when the account has it, and the new proof of identity the server asks for critical actions from outside the house.
- **The assistant,** written commands to the voice service of the server with the confirmation bound to the person for arming and disarming, behind the lock.
- **Alarms that reach the phone:** notices for a node reaching HIGH, a silent camera, a device or equipment alarm and, while armed, a node that goes offline or silent; the alarm of a duress PIN is never shown or announced. Each event is announced once whether it arrives by reading or by push (the id of the event is the key), and the first reading only records where the history stands. Pushes through Firebase are optional and need the Firebase file of the installation.
- **Cameras:** a grid where only the pictures on screen run (six at most), a full view with a pad to move the camera and a snapshot, and a stream that is asked for again after 1, 2, 4... seconds (30 at most) when it drops. The picture comes from the server: the app never has a camera password or an RTSP address.
- **Devices** with On / Off, a confirmation for a circuit or a critical device, and the status, history and preflight of arming ("what would be left blind or noisy").
- **Eight languages** (English, Spanish, German, French, Italian, Japanese, Chinese and Portuguese of Portugal) for every text, the help, and the permission texts of the system; a check keeps every phrase of the sources in all the tables.
- **Checks that need no Mac:** `tools/ios_lint.py` verifies the structure of the project, the eight tables against the phrases of the sources, that the app calls only paths the Android client calls (and that the OpenAPI of the common repository knows them), the permissions, and that no secret or camera address is in the sources.
- **What it does not do:** it does not watch in the background (iOS does not allow a closed app to query the server), so alarms reach a closed app only through push; it has not been run on a device yet.
